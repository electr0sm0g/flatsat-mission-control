Goal: every finding is (1) real firmware, (2) mirrored bit-for-bit in a simulator, (3) proven by one executable PoC that runs on both.

Everything a PoC can touch from the wire rides on core0; the workers are the interesting part — and they are time-gated.

The problem: testing time-dependent firmware

  • The mission model, FDIR, scheduler and radio workers advance on the mission clock.
  • On the simulator that clock only moves inside advance() — explicit time windows.
  • On the board, real time moves 1:1 and the workers run whenever they feel like it.

Different tick instants ⇒ different behaviour ⇒ no parity. The classic sim-vs-hardware lie: “passes on both” but not at the same instants.

Fix: give the firmware the same window-only clock. →

The bench parity trick: FEED windows

60.0× cold-boot scale, re-arm between PoCs → every PoC starts from the same reference state. One PoC, two targets, same instants.

Flagship: V-36 — full initial access

The security model's keystone is sensor data:

  1. Spoof GPS 9500 km away (NMEA override, no checksum) → GS range gate locks out
  2. Spoof back into the 35 km footprint — the plausibility gate (500 km/s) stops the instant hop, not the 60 s-spread one (158 km/s)
  3. Answer the handshake: challenge ^ 0xC0DEFACE (static key, in the image)
  4. SET_MISSION_MODE(PAYLOAD) → privileged control, unauthenticated uplink

Chain with V-28 (predictable challenge) → the handshake becomes passive. Full walkthrough: docs/KILLCHAIN-V36.md.

Memory corruption → RCE (V-14)

A MEMCPY telecommand takes “all three” arguments from the frame — dst, src, len — bounded only by the address map.

# write-what-where: overwrite the vector table
dst = VTOR + 3*4          # IRQ3 handler slot
src = shellcode_in_sram
len = 12
  • VTOR redirect → attacker code runs on the RP2040 (core context of the mission loop)
  • Same PoC, same result: simulator transcript and board transcript both end POC OK
  • Fix: bounds at the frame layer + flash-locked code region (VTOR immutable)

Persistence: unsigned OTA → flash trojan (V-18 → V-20)

  • V-18: OTA image push verified with CRC-16 only — a checksum is not a signature
  • V-20: the FDIR contingency dictionary is flash-resident and TC-writable → executable trojan
  • V-19: scheduled task queue replays after any reboot — it survives the reset you use to “clean up”

Result: an attacker with one uplink owns the next boot — and the boot after that. Signed OTA + signed stores is the answer (docs/DEFENSE.md, groups 7–8).

Impact: the crash PoCs are the finding

  • v003 — BROADCAST 0xFFFD underflow → unbounded memcpy → worker crash
  • v015 — no watchdog: the vehicle hangs until a physical power cycle
  • v135 — downlink saturation floods the TM path

On the real board these wedge the silicon (DTR NAK'd, replug-only). That is not a test bug — it is the impact, captured on tape in evidence-hw/.

The health gate in the hardware sweep stops a doomed run early instead of burning 10 min/PoC.
